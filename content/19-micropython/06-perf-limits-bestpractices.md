MicroPython запускает тот же Python, что и твой компьютер, но на железе с очень скромными ресурсами. Относиться к ним нужно как к дорогому топливу: разумно. Этот урок — про то, как писать программы, которые не «съедают» плату и не зависают.

## Сколько у нас памяти

У ESP32 обычно 320 КБ ОЗУ, у Raspberry Pi Pico — 264 КБ. Это в тысячи раз меньше, чем у ноутбука. Проверь сам:

```python
import gc
import micropython

gc.collect()                 # собрать мусор
print("Свободно:", gc.mem_free(), "байт")
print("Занято:", gc.mem_alloc(), "байт")
micropython.mem_info()       # подробный отчёт
```

`gc` — сборщик мусора: он находит объекты, которые больше не нужны, и освобождает память. `gc.collect()` запускает сбор вручную. `micropython.mem_info()` печатает сводку. Если свободной памяти мало — программа начнёт падать с `MemoryError`.

## Почему в циклах не надо создавать объекты

Самая частая причина утечек — создание новых объектов в цикле. Взгляни:

```python
bad = ""
for i in range(1000):
    bad = bad + str(i)   # каждый раз создаётся НОВАЯ строка!
```

Каждая итерация создаёт новую копию строки, а старую оставляет мусору. Это и медленно, и память съедает. Правильный способ — собрать части в список и склеить один раз:

```python
good = "".join(str(i) for i in range(1000))
```

Правило: **не создавай объекты в цикле, если можно собрать их потом**. Это касается строк, списков, словарей и буферов.

## bytearray вместо списка

Для хранения байтов (данные датчиков, пакеты, изображения) используй `bytearray` — он занимает ровно 1 байт на элемент, в отличие от списка целых чисел:

```python
buf = bytearray(100)     # 100 байт
lst = [0] * 100          # список — на порядок больше
import sys
print(sys.getsizeof(buf), sys.getsizeof(lst))
```

`sys.getsizeof()` показывает размер объекта. На MicroPython разница легко в 4–10 раз — для больших буферов это критично.

## Таймеры вместо ожидания

Цикл `while True:` с `time.sleep()` — простой, но пока программа спит, она не может делать ничего другого. Для периодических действий лучше аппаратный таймер: он вызывает функцию сам, без участия главного цикла.

```python
import machine
import time

def tick(timer):
    print("Тик!")

timer = machine.Timer(period=500, mode=machine.Timer.PERIODIC, callback=tick)

while True:
    time.sleep(1)   # главная программа занята своим делом
```

Таймер каждые 500 мс вызывает `tick()`, а главный цикл в это время делает своё. Важно: внутри callback нельзя делать долгих операций (сон, сложные вычисления) — это блокирует всё остальное.

## Прерывания от пинов

То же самое касается кнопок: вместо опроса в цикле можно повесить обработчик **прерывания** (IRQ), который вызовется сам при изменении уровня:

```python
from machine import Pin
count = 0

def on_press(pin):
    global count
    count += 1
    print("Нажато:", count)

button = Pin(14, Pin.IN, Pin.PULL_UP)
button.irq(trigger=Pin.IRQ_FALLING, handler=on_press)

while True:
    pass
```

`IRQ_FALLING` — срабатывание при падении уровня (нажатие). Обработчик должен быть коротким: никаких `sleep`, минимум работы — иначе можно пропустить события или поймать сбой.

## Устойчивость: исключения и watchdogs

В реальных устройствах всё ломается: датчик молчит, сеть пропадает, датчик зависает. Поэтому: оборачивай опасные операции в `try/except` (как с DHT22), а если устройство должно работать сутками — добавь сторожевой таймер `machine.WDT`, который перезагрузит плату, если программа зависнет:

```python
wdt = machine.WDT(timeout=5000)   # 5 секунд
while True:
    # работа устройства...
    wdt.feed()   # подтвердить: я жив
```

## Итог: чек-лист лучших практик

1. Не создавай объекты в циклах — собирай их потом.
2. Храни байтовые данные в `bytearray`, а не в списках.
3. Следи за памятью: `gc.mem_free()` перед длительными операциями.
4. Периодические действия — через `Timer`, а не через `sleep`.
5. Кнопки и датчики — через `irq`, а не через опрос в цикле.
6. Все внешние операции (сеть, датчики) — в `try/except`.
7. Сторожевой таймер для длительной работы.
8. Не используй `float`, если хватает целых чисел, — они занимают больше памяти.

С этими инструментами плата выдержит и сутки непрерывной работы, и сложные проекты. Переходи к задачам — они закрепят каждый инструмент.

### Разбор 1
Программа:

```python
import gc

gc.collect()
a = gc.mem_free()
lst = [0] * 10000
b = gc.mem_free()
print("До:", a)
print("После:", b)
print("Разница:", a - b)
```

Что здесь происходит? `gc.mem_free()` — сколько байт свободно сейчас. После создания списка из 10 000 нулей свободной памяти стало меньше — но не на 10 000 байт, а меньше, потому что список хранит **ссылки** на объекты, а не копии чисел: все `0` — это один и тот же объект, и список — это массив из 10 000 ссылок по несколько байт. Разница примерно равна размеру массива ссылок. Это важное понимание: список — это «полка с ярлыками», а сами данные лежат отдельно.

### Разбор 2
Программа:

```python
import sys
buf = bytearray(1000)
lst = [0] * 1000
print("bytearray:", sys.getsizeof(buf))
print("list:", sys.getsizeof(lst))
print("В раз:", sys.getsizeof(lst) // sys.getsizeof(buf))
```

Что здесь происходит? `bytearray(1000)` выделяет ровно 1000 байт — по одному на элемент. Список `[0] * 1000` содержит 1000 ссылок по 4 байта плюс служебные данные — обычно в 4–10 раз больше. Поэтому для хранения байтовых данных (показания датчиков, изображения, сетевые пакеты) всегда используй `bytearray` — это экономия памяти, которую плата оценит.

### Разбор 3
Программа:

```python
import machine
import time

n = 0

def tick(timer):
    global n
    n += 1
    print("Тик:", n)

timer = machine.Timer(period=500, mode=machine.Timer.PERIODIC, callback=tick)

while True:
    print("Главный цикл")
    time.sleep(1)
```

Что здесь происходит? Таймер — это аппаратный «будильник», который вызывает `tick()` каждые 500 мс независимо от того, что делает главный цикл. Поэтому на экране сообщения перемешиваются: `Тик` и `Главный цикл` идут «параллельно». Если бы мы использовали только `sleep`, программа смогла бы делать только одно действие за раз. Обрати внимание: `tick()` должен быть коротким — он выполняется «в тени» основного кода.

### Разбор 4
Программа:

```python
import time

# Наивный вариант
start = time.ticks_ms()
s = ""
for i in range(1000):
    s += str(i)
naive = time.ticks_diff(time.ticks_ms(), start)

# Через join
start = time.ticks_ms()
s = "".join(str(i) for i in range(1000))
joined = time.ticks_diff(time.ticks_ms(), start)

print("Конкатенация:", naive, "мс")
print("join:", joined, "мс")
```

Что здесь происходит? `s += str(i)` на каждой итерации создаёт новую строку: старую — в мусор, новую — длиннее на символ. Это квадратичная сложность: 1000 итераций — миллионы операций копирования. `join` один раз проходит по списку частей и склеивает их за один проход. Разница в десятки и сотни раз — и она растёт с размером. На реальной плате, где каждая миллисекунда на счету, это заметно сразу.

### Разбор 5
Программа:

```python
from machine import Pin
import gc
import time

count = 0

def on_press(pin):
    global count
    count += 1

button = Pin(14, Pin.IN, Pin.PULL_UP)
button.irq(trigger=Pin.IRQ_FALLING, handler=on_press)

while True:
    print("Счётчик:", count)
    gc.collect()
    time.sleep(2)
```

Что здесь происходит? Прерывание срабатывает в момент падения уровня — ровно в момент нажатия, без опроса в цикле. Обработчик делает только `count += 1` — коротко и быстро, поэтому события не пропускаются. Печать и сборка мусора вынесены в главный цикл, чтобы не тормозить обработчик. Антидребезг здесь не нужен: `IRQ_FALLING` срабатывает один раз за фронт, и если дребезг даёт лишние фронты, их отсекают уже на уровне железа или добавляют крошечную задержку в обработчике.
