Модель отлично работала на тестовой выборке — но мир не стоит на месте. Пользователи меняют поведение, меняются цены, сезоны, рынок. Если модель «застыла» в том виде, в каком её обучили, её качество в проде будет медленно, но верно падать. Задача MLOps — **заметить это раньше, чем пользователи заметят проблему**. Это и есть мониторинг моделей.

## Два вида дрейфа

**Дрейф данных (data drift)** — изменилось распределение *входных* признаков. Пример: модель скоринга обучена, когда средний возраст клиента был 35 лет, а теперь клиенты стали моложе — распределение `age` сдвинулось. Модель получает данные, которых «не видела».

**Концептуальный дрейф (concept drift)** — изменилась сама *связь* между признаками и целью. Пример: после изменения законодательства тот же набор признаков стал хуже предсказывать дефолт. Входы те же, «закон природы» изменился.

Для первого случая есть прямые методы — сравнение распределений. Второй сложнее: ведь истинных ответов на живых данных у нас нет (разве что с задержкой). Поэтому используют **прокси-метрики**: распределение предсказаний, средняя уверенность модели, число отказов, задержки ответов.

## Индекс стабильности популяции (PSI)

Самый популярный способ сравнить два распределения — **PSI** (Population Stability Index). Мы разбиваем эталонное распределение (например, предсказания на дате обучения) на интервалы, а затем смотрим, как распределились по тем же интервалам новые данные:

```python
import numpy as np

def psi(expected, actual, bins=10):
    # Границы интервалов берём из эталона
    breaks = np.percentile(expected, np.linspace(0, 100, bins + 1))
    breaks[0], breaks[-1] = -np.inf, np.inf

    hist_e, _ = np.histogram(expected, bins=breaks)
    hist_a, _ = np.histogram(actual, bins=breaks)

    pe = hist_e / hist_e.sum()   # доля эталона в каждом интервале
    pa = hist_a / hist_a.sum()   # доля новых данных
    # Защита от деления на ноль
    pe = np.clip(pe, 1e-6, None)
    pa = np.clip(pa, 1e-6, None)

    return float(np.sum((pa - pe) * np.log(pa / pe)))
```

Классические пороги:

- `PSI < 0.1` — дрейфа практически нет;
- `0.1 ≤ PSI < 0.25` — умеренный дрейф, стоит понаблюдать;
- `PSI ≥ 0.25` — сильный дрейф, модель нужно переобучать.

## Проверяем на симуляции

```python
rng = np.random.default_rng(42)
baseline = rng.normal(0.5, 0.1, size=10000)   # «обучение»
old = rng.normal(0.5, 0.1, size=10000)        # тот же мир
new = rng.normal(0.7, 0.1, size=10000)        # мир сдвинулся

print("PSI(old, old):", round(psi(baseline, old), 4))   # ≈ 0
print("PSI(old, new):", round(psi(baseline, new), 4))   # большой
```

`psi(baseline, old)` даст ~0 (распределения одинаковые), а `psi(baseline, new)` — большое значение. Так PSI превращается в «сигнализацию»: сравниваешь текущее распределение предсказаний с эталонным — и сразу видишь дрейф.

## Алерты

Настоящий мониторинг не просто считает число — он оповещает. Оборачиваем проверку в функцию с порогом и логированием:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")

def check_drift(expected, actual, threshold=0.25):
    value = psi(expected, actual)
    if value >= threshold:
        logging.warning("Дрейф: PSI = %.3f >= %.2f — нужен ретраининг!", value, threshold)
    else:
        logging.info("ОК: PSI = %.3f", value)
    return value

check_drift(baseline, new)
check_drift(baseline, old)
```

В проде `logging.warning` уходит в систему сбора логов (Sentry, ELK, Grafana), откуда сообщения приходят дежурным — а при тяжёлых дрейфах срабатывает автоматический пейджинг.

## Мониторинг ресурсов

Дрейф — не единственная беда. Сервис может просто умереть от перегрузки. Поэтому в каждом проде есть сбор системных метрик — через `psutil`:

```python
import psutil, json, time

def collect_metrics():
    return {
        "timestamp": time.time(),
        "cpu_percent": psutil.cpu_percent(interval=0.1),
        "mem_percent": psutil.virtual_memory().percent,
        "disk_percent": psutil.disk_usage("/").percent,
    }

with open("metrics.json", "w") as f:
    json.dump(collect_metrics(), f, indent=2)
```

Эти же данные отдаёт `/healthz` из прошлого урока. Собранные метрики отправляются в систему мониторинга, где строят графики и выставляют пороги для алертов.

### Разбор 1
Решение:

```python
import numpy as np

def psi(expected, actual, bins=10):
    breaks = np.percentile(expected, np.linspace(0, 100, bins + 1))
    breaks[0], breaks[-1] = -np.inf, np.inf

    hist_e, _ = np.histogram(expected, bins=breaks)
    hist_a, _ = np.histogram(actual, bins=breaks)

    pe = hist_e / hist_e.sum()
    pa = hist_a / hist_a.sum()
    pe = np.clip(pe, 1e-6, None)
    pa = np.clip(pa, 1e-6, None)

    return float(np.sum((pa - pe) * np.log(pa / pe)))

rng = np.random.default_rng(42)
b1 = rng.normal(0.5, 0.1, size=10000)
b2 = rng.normal(0.5, 0.1, size=10000)
print("PSI:", round(psi(b1, b2), 4))
```

Разбор шагов. `np.percentile` находит границы интервалов так, чтобы в каждый из 10 попало примерно 10% эталона. Затем `np.histogram` с этими границами раскладывает оба распределения по одним и тем же «корзинкам». `pe` и `pa` — доли точек в каждой корзинке; `np.clip` защищает от нуля (иначе логарифм даст -inf). Сама формула `(pa - pe) * log(pa / pe)` суммируется — это и есть PSI. При одинаковых распределениях доли совпадают, каждый член ≈ 0, и сумма ≈ 0. Это «санитарная» проверка: если PSI для одинаковых выборок не нулевой, значит, где-то ошибка (например, в границах или в порядке аргументов).

### Разбор 5
Решение:

```python
rng = np.random.default_rng(1)
baseline = rng.normal(0.5, 0.1, size=10000)

weeks = []
for i in range(6):
    weeks.append(rng.normal(0.5, 0.1, size=10000))
for i in range(6):
    weeks.append(rng.normal(0.65, 0.12, size=10000))

alarm_week = None
for idx, week_data in enumerate(weeks):
    value = psi(baseline, week_data)
    print(f"Неделя {idx + 1}: PSI = {round(value, 4)}")
    if alarm_week is None and value > 0.25:
        alarm_week = idx + 1

print("Первая тревожная неделя:", alarm_week)
```

Разбор шагов. Первые 6 недель живут в том же мире, что эталон: PSI ≈ 0. С 7-й недели распределение сдвигается (`0.65` вместо `0.5`) — PSI растёт. Цикл с `enumerate` печатает все 12 строк, а `alarm_week` запоминает первую неделю, где PSI превысил 0.25. Это минимальная модель «сигнализации»: те же шаги в проде приводят к автоматическому созданию тикета или оповещению команды. Так мониторинг превращается в управляемый процесс: ты не узнаёшь о дрейфе от пользователей, а узнаёшь от собственной системы — раньше.
