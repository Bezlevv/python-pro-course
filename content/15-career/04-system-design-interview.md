Системный дизайн — это проектирование архитектуры сервиса, который выдержит нагрузку реального мира. На интервью тебе дадут задачу вроде «спроектируй сервис коротких ссылок» и будут смотреть не на точные цифры, а на ход мыслей: умеешь ли ты собирать требования, оценивать масштаб и принимать обоснованные решения.

## План ответа

Хороший ответ идёт по шагам:

1. **Требования**: функциональные (что система делает) и нефункциональные (сколько пользователей, какая задержка, доступность).
2. **Оценка масштаба**: сколько запросов в секунду (QPS), сколько данных хранить, какой нужен трафик.
3. **High-level дизайн**: компоненты (клиент, балансировщик, серверы, БД, кэш, очереди) и поток запроса.
4. **Детализация**: хранилище, кэширование, rate limiting, отказоустойчивость.
5. **Оптимизации**: что узкое место и как его снять.

## Ключевые концепции

- **Масштабируемость**: горизонтальная (добавляем машины) и вертикальная (усиливаем одну).
- **Доступность и согласованность**: CAP-теорема говорит, что распределённая система не может одновременно гарантировать согласованность (C), доступность (A) и устойчивость к разделению сети (P). На практике почти всегда выбирают P, а между C и A — компромисс.
- **Балансировщик** распределяет запросы между серверами.
- **CDN** — сеть доставки статического контента (картинки, CSS, JS) ближе к пользователю.
- **Кэш** (Redis) хранит часто читаемые данные в памяти — чтение в десятки раз быстрее, чем из БД.
- **Очереди** (RabbitMQ, Kafka) развязывают компоненты: система не падает, если сервис-приёмник временно недоступен.
- **Базы данных**: SQL (PostgreSQL, MySQL) — транзакции, сложные запросы, связи; NoSQL (MongoDB, Cassandra) — гибкие схемы, горизонтальное масштабирование.
- **Шардирование** — разбиение данных по нескольким серверам по ключу (например, по user_id).
- **Репликация** — копии данных (ведущий — ведомые) для отказоустойчивости.
- **Rate limiting** — ограничение числа запросов (антиспам, защита от перегрузки).

## Распространённые ошибки

- Молчать и ждать, пока интервьюер задаст вопрос.
- Сразу углубляться в детали одного компонента, забыв об общей картине.
- Называть технологии без объяснения, зачем они нужны.
- Игнорировать отказы: «а что будет, если сервер умер?» — обязательный вопрос.

## Пример: сервис коротких ссылок

Поток запроса: клиент → балансировщик → сервер приложения → кэш Redis (проверка) → БД. Короткий код генерируется при создании ссылки, хранится вместе с длинным URL, а при переходе сервер находит длинный URL и возвращает редирект. Читаемые ссылки кэшируются, поэтому горячие переходы не долбят БД.

### Подсказка 1
Считай по шагам: сначала сколько ссылок создаётся в сутки (10 млн × 20%), затем подели на 100 000 секунд. Переходы: 10 млн × 10 переходов, подели на 100 000. Годовое накопление — суточное количество × 365. Объём — число записей × 200 байт, не забудь перевести в мегабайты/гигабайты.

### Подсказка 2
Нарисуй поток запроса словами: клиент идёт на балансировщик, тот отдаёт запрос одному из серверов приложения. Сервер сначала проверяет кэш, и только при промахе идёт в БД. При создании ссылки сервер генерирует короткий код, сохраняет запись в БД и кладёт её в кэш. При переходе — читает кэш, при промахе — БД, затем возвращает редирект.

### Подсказка 3
Данные ссылки — это жёсткая структура: короткий код (уникальный), длинный URL, дата создания, счётчик переходов. Паттерн доступа — точечное чтение по ключу. Транзакции нужны при вставке с проверкой уникальности. Подумай про индекс по короткому коду: он должен быть уникальным. Mongo тоже подойдёт, но обоснуй, почему PostgreSQL надёжнее для транзакционной вставки.

### Подсказка 4
Fixed window простое, но позволяет 20 запросов в момент смены окна. Sliding window точнее: учитывает точное время запросов. Token bucket разрешает короткие всплески: в ведре лежит N токенов, каждый запрос забирает один, а ведро пополняется со скоростью N/10 в секунду. ### Подсказка 5

### Разбор 1
Решение:

```python
DAU = 10_000_000
percent_creators = 0.20
transitions_per_active = 10
seconds_per_day = 100_000
record_size = 200

links_per_day = DAU * percent_creators            # 2 млн ссылок в сутки
links_per_sec = links_per_day / seconds_per_day   # 20 ссылок/с
transitions_per_sec = DAU * transitions_per_active / seconds_per_day  # 1000 переходов/с
links_per_year = links_per_day * 365              # 730 млн ссылок
storage_per_year = links_per_year * record_size    # 146 млрд байт = 146 ГБ?print(f"Новых ссылок в секунду: {links_per_sec:.0f}")
print(f"Переходов в секунду: {transitions_per_sec:.0f}")

print(f"Хранилище за год: {storage_per_year / 1e9:.1f} ГБ")
```

Вывод:

```
Переходов в секунду: 1000
Ссылок за год: 730,000,000
Хранилище за год: 146.0 ГБ
```

Что здесь происходит? Мы оцениваем порядок величин, а не точные цифры: 20 ссылок в секунду — копейки для любой БД, а 1000 переходов в секунду — средняя нагрузка, которую держит один современный сервер. Главный вывод для интервью: узкое место не в БД, а в точности кода и кэшировании. Такие оценки показывают, что ты мыслишь масштабами — это и есть суть задач на дизайн.

### Разбор 2
Схема:

```
Клиент (браузер)

   ▼
Балансировщик (NGINX, HAProxy)
   │
   ▼
Сервер приложения (FastAPI/Django)
   │                    │
   ├──► Кэш Redis ◄────┘
   │       │
   │       └──► База данных PostgreSQL

```

Создание ссылки: клиент отправляет POST с длинным URL → балансировщик → сервер приложения генерирует короткий код → вставляет запись в PostgreSQL → кладёт код и URL в Redis. Переход: клиент открывает короткую ссылку → сервер сначала ищет код в Redis → при промахе читает PostgreSQL → возвращает 302-редирект на длинный URL.

Что здесь происходит? Компоненты разделены по обязанностям: балансировщик распределяет нагрузку, приложение содержит логику, Redis ускоряет чтение, PostgreSQL — источник истины. Это называется high-level дизайн: ты показал общую картину, не утонув в деталях, и описал два главных потока. Дальше на интервью интервьюер углубляется туда, куда захочет.

### Разбор 3
Выбор PostgreSQL. Обоснование:

1. **Структура данных** — жёсткая: короткий код, длинный URL, дата создания, счётчик. Табличная схема подходит идеально, поля не меняются от записи к записи.
2. **Паттерн доступа** — точечное чтение по уникальному ключу (короткому коду). PostgreSQL поддерживает уникальный индекс, что даёт O(log n) поиск.
3. **Транзакционность** — создание ссылки должно быть атомарным: вставка с проверкой уникальности кода. PostgreSQL гарантирует ACID.
4. **Масштабирование** — можно начать с одной реплики, а при росте шардировать по хешу кода или перейти на читающие реплики.

Схема таблицы:

```sql
CREATE TABLE links (
    code VARCHAR(10) PRIMARY KEY,
    url TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now(),
    clicks BIGINT DEFAULT 0
);
```

Что здесь происходит? Выбор БД — это спор: оба варианта рабочие. Ключ к хорошему ответу — обоснование через требования: жёсткая схема, транзакции и точечный доступ тянут к PostgreSQL. Уникальный индекс по `code` — это ответ на самый частый запрос (переход по ссылке). Такой ответ показывает, что ты выбираешь инструмент под задачу, а не по моде.

### Разбор 4
Выбор: token bucket. Реализация в Redis:

```python
import redis, time

r = redis.Redis()

def allow_request(user_id, bucket_size=10, refill=10, window=1):
    key = f"tb:{user_id}"
    # INCR увеличивает счётчик, EXPIRE ставит TTL на окно
    token = r.incr(key)
    if token == 1:
        r.expire(key, window)
    return token <= bucket_size
```

Описание алгоритмов:

- **Fixed window**: счётчик на секунду. Просто, но на границе окна пользователь может отправить 20 запросов подряд (10 в конце секунды и 10 в начале следующей).
- **Sliding window**: храним метки времени запросов и считаем те, что попадают в последнюю секунду. Точнее, но дороже по памяти.
- **Token bucket**: ведро на 10 токенов, каждый запрос забирает токен, ведро пополняется со скоростью 10 токенов в секунду. Разрешает короткие всплески, но сглаживает среднюю нагрузку.

При превышении лимита сервер возвращает HTTP 429 Too Many Requests с заголовком `Retry-After`. Что здесь происходит? Мы выбрали token bucket за его гибкость (всплески) и простоту реализации через `INCR` + `EXPIRE`. На интервью важно объяснить не только «что», но и «почему», и упомянуть поведение при превышении лимита.

### Разбор 5
Решение:

- Ключ Redis: `link:{short_code}` → значение: длинный URL; TTL: 24 часа.
- Стратегия обновления: при удалении ссылки приложение удаляет и запись из Redis; при создании — кладёт её в кэш сразу. TTL защищает от «зависших» ключей, если удаление пропущено.
- Hit ratio: 20% ссылок обеспечивают 80% переходов. Если все эти горячие ссылки помещаются в кэш, то из 100 переходов 80 обслуживаются Redis, и в БД уходит 20 запросов. Это снижает нагрузку на БД в 5 раз.

Что здесь происходит? Кэширование бьёт точно в горячее место: 80% трафика отсекается от БД одним Redis. Вероятность промаха снижается ещё, если читать «лениво»: при промахе загружать значение из БД и класть в кэш. На интервью обязательно спроси себя: «что будет при рестарте Redis?» — ответ: БД выдержит промахи, пока кэш разогревается, а пиковая нагрузка переживёт благодаря распределению запросов.
