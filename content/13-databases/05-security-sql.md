## Что такое SQL-инъекция

SQL-инъекция (SQL injection) — атака, при которой злоумышленник «подмешивает» свой SQL в твой запрос. Она возникает, когда ты собираешь SQL-строку конкатенацией с пользовательским вводом:

```python
# УЯЗВИМЫЙ КОД — никогда так не делай!
def login_vulnerable(username, password):
    cur.execute(
        "SELECT id FROM users WHERE username = '" + username +
        "' AND password = '" + password + "'"
    )
    return cur.fetchone()
```

Что произойдёт, если в поле username ввести `' OR '1'='1' --`? Запрос превратится в:

```sql
SELECT id FROM users WHERE username = '' OR '1'='1' --' AND password = ''
```

Комментарий `--` отрезает остаток условия, а `OR '1'='1'` истинно всегда — злоумышленник «вошёл» без пароля. Ещё опаснее: ввод `'; DROP TABLE users; --` удалит таблицу.

## Параметризованные запросы — главная защита

Никогда не подставляй значения в SQL конкатенацией. Передавай их как параметры: драйвер отправит значения отдельно от текста запроса, и они будут интерпретироваться как данные, а не как код.

```python
def login_safe(username, password):
    cur.execute(
        "SELECT id FROM users WHERE username = ? AND password = ?",
        (username, password),
    )
    return cur.fetchone()
```

Символ `?` — плейсхолдер sqlite3. В psycopg (PostgreSQL) используют `%s`, а именованные плейсхолдеры — `:name`:

```python
import psycopg2
conn = psycopg2.connect("dbname=shop user=postgres")
cur = conn.cursor()
cur.execute(
    "SELECT id FROM users WHERE username = %s AND password = %s",
    (username, password),
)
```

Подход везде одинаковый: база получает текст запроса и значения раздельно и не даёт значениям изменить смысл запроса.

## Ловушки, которые не являются защитой

- **Экранирование кавычек** вручную — легко ошибиться; лучше параметры.
- **Чёрный список слов** (запрет `DROP`, `SELECT` и т.п.) — обходится вариантами написания, комментариями и кодировками.
- **f-строки «только для чисел»** — число вроде `1; DROP TABLE users; --` тоже строка.

## ORM и безопасность

SQLAlchemy и Django ORM сами параметризуют запросы, поэтому типичный код на ORM безопасен. Но и здесь есть ловушки: сырой SQL через `text()` нужно параметризовать bindparams:

```python
from sqlalchemy import text
result = session.execute(
    text("SELECT id FROM users WHERE username = :u"),
    {"u": username},
)
```

## Валидация ввода и принцип наименьших привилегий

Параметризация закрывает инъекции, но это не весь оборонный периметр:

- **Валидируй тип и длину ввода**: email должен содержать @, возраст — число от 0 до 120.
- **Пользователь СУБД должен иметь минимально необходимые права**: веб-приложению обычно хватает SELECT/INSERT/UPDATE/DELETE на свои таблицы, но не DROP/CREATE.
- **Не раскрывай служебные сообщения об ошибках БД** пользователю — они помогают атакующему понять структуру базы.
- Регулярно делай резервные копии — но лучше не доводить до их восстановления.

## Демонстрация атаки

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript("""
CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT, password TEXT);
INSERT INTO users VALUES (1, 'admin', 'secret123'), (2, 'anya', 'qwerty');
""")

attack = "' OR '1'='1' --"
cur.execute("SELECT id FROM users WHERE username = '" + attack + "'")
print("Уязвимо:", cur.fetchall())    # [(1,), (2,)] — вся база!

cur.execute("SELECT id FROM users WHERE username = ?", (attack,))
print("Безопасно:", cur.fetchall())  # []
```

## Итог

### Подсказка 1
База создаётся через `sqlite3.connect(":memory:")` и `executescript` с CREATE TABLE и INSERT. Обрати внимание, как кавычки в строке атаки закрывают строковый литерал в SQL, а `--` превращает остаток в комментарий.

### Подсказка 2
В безопасной версии значения передаются вторым аргументом `execute` кортежем: `cur.execute("... WHERE username = ?", (username,))`. Драйвер передаст строку атаки как обычное значение, и она не изменит запрос.

### Подсказка 3
Сначала замени в вводе `%` на `\%`, а `_` на `\_` (через replace). Затем добавь по краям `%` для поиска подстроки и передай как параметр. В SQL добавь `ESCAPE '\'`, чтобы `\` работал как экранирующий символ. В Python-строке SQL бэкслеш пиши как `\\`.

### Подсказка 4
Белый список — это словарь, где ключи — безопасные «публичные» имена, а значения — реальные имена колонок. Выбирай значение через `.get(sort_key)` и проверяй `None`. Затем строй `ORDER BY <col>` с уже проверенным значением — без пользовательского ввода в запросе.

### Подсказка 5
Оберни `cur.execute(query, params)` и `cur.fetchall()` в `try/except Exception`. В except возвращай строку `"Ошибка запроса"`. Текст `repr(e)` или `str(e)` никуда не выводи — только логируй на своём сервере.

### Разбор 1
Решение:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript("""
CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT, password TEXT);
INSERT INTO users VALUES (1, 'admin', 'secret123'), (2, 'anya', 'qwerty');
""")

def login_vulnerable(cur, username):
    cur.execute(
        "SELECT id FROM users WHERE username = '" + username + "'"
    )
    return cur.fetchall()

attack = "' OR '1'='1' --"
print(login_vulnerable(cur, attack))
```

Результат:

```
[(1,), (2,)]
```

Что здесь происходит? Пользовательский ввод вставляется прямо в SQL-строку. Атака `' OR '1'='1' --` закрывает строковый литерал первой кавычкой, добавляет вечно истинное условие `OR '1'='1'` и гасит остаток условия комментарием `--`. Запрос превращается в `SELECT id FROM users WHERE username = '' OR '1'='1' --'`, который возвращает все строки таблицы. Именно так выглядят реальные обходы авторизации. Если бы мы подставили `'; DROP TABLE users; --` — последствия были бы разрушительными.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript("""
CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT, password TEXT);
INSERT INTO users VALUES (1, 'admin', 'secret123'), (2, 'anya', 'qwerty');

def login_safe(cur, username):

print(login_safe(cur, attack))
```

Результат:

```

```

Что здесь происходит? Вместо конкатенации значение передаётся отдельно через плейсхолдер `?`. Драйвер отправляет в SQLite текст запроса и значение раздельно, и SQLite интерпретирует строку `' OR '1'='1' --` как обычные данные — как текст для сравнения с колонкой username. Совпадений нет, результат пуст. В psycopg2 плейсхолдер `%s`, в SQLAlchemy text() — `:name`, но принцип один: значения никогда не становятся частью текста запроса. Это главная защита от инъекций.

### Разбор 3
Решение:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript("""
CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO products (name) VALUES
    ('Клавиатура 100% механическая'),
    ('Клавиатура проводная'),
    ('Мышь оптическая');
""")

def search_products(conn, pattern):
    escaped = pattern.replace("%", "\\%").replace("_", "\\_")
    cur = conn.cursor()
    cur.execute(
        "SELECT name FROM products WHERE name LIKE ? ESCAPE '\\'",
        (f"%{escaped}%",),
    )
    return [row[0] for row in cur.fetchall()]

print(search_products(conn, "100%"))
```

Результат:

```
['Клавиатура 100% механическая']
```

Что здесь происходит? В LIKE символы `%` и `_` — спецсимволы: `%` означает «любая последовательность», `_` — «любой один символ». Если не экранировать, поиск `"100%"` нашёл бы всё, что содержит «100» с любым продолжением — и, например, «100500» тоже. Мы заменяем `%` на `\%` и `_` на `\_`, а клаузула `ESCAPE '\'` говорит базе, что бэкслеш — экранирующий символ. Обрати внимание на двойной бэкслеш в Python-строках: `"\\%"` — это строка из двух символов `\` и `%`. Ввод всё ещё передаётся параметром, так что инъекция невозможна.

### Разбор 4
Решение:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript("""
CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, price REAL);
INSERT INTO products (name, price) VALUES
    ('Клавиатура', 1500),
    ('Мышь', 800),
    ('Монитор', 12000);
""")

ALLOWED = {"price": "price", "name": "name"}

def get_products_sorted(cur, sort_key):
    col = ALLOWED.get(sort_key)
    if col is None:
        raise ValueError("Недопустимая сортировка")
    cur.execute(f"SELECT name, price FROM products ORDER BY {col}")
    return cur.fetchall()

print(get_products_sorted(cur, "price"))
try:
    get_products_sorted(cur, "price; DROP TABLE products")
except ValueError as e:
    print("Заблокировано:", e)
print(cur.execute("SELECT COUNT(*) FROM products").fetchone()[0])
```

Результат:

```
[('Мышь', 800.0), ('Клавиатура', 1500.0), ('Монитор', 12000.0)]
Заблокировано: Недопустимая сортировка
3
```

Что здесь происходит? Имена колонок нельзя передавать как параметры — параметры подставляются туда, где ожидается значение, а не идентификатор. Поэтому для ORDER BY используется белый список: пользователь выбирает из безопасных ключей, а реальное имя колонки берётся из словаря. Ввод `price; DROP TABLE products` в словаре отсутствует, поэтому функция сразу бросает ValueError, и вредоносный SQL даже не достигает базы. Таблица продуктов цела: в ней по-прежнему три строки.

### Разбор 5
Решение:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.executescript("""
CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO products (name) VALUES ('Клавиатура'), ('Мышь');
""")

def safe_query(cur, query, params):
    try:
        cur.execute(query, params)
        return cur.fetchall()
    except Exception:
        return "Ошибка запроса"

print(safe_query(cur, "SELECT name FROM products WHERE no_such_column = ?", (1,)))
```

Результат:

```
Ошибка запроса
```

Что здесь происходит? Запрос обращается к несуществующей колонке, и SQLite бросает OperationalError. Функция ловит любое исключение и возвращает нейтральное сообщение, не раскрывая деталей: ни текста SQL, ни имён колонок, ни вида базы. В реальном приложении текст ошибки можно логировать на своём сервере, но пользователю его показывать нельзя — атакующий использует такие сообщения, чтобы понять структуру базы и подобрать следующий шаг атаки. Помни: безопасность — это слои: параметризация + валидация + скрытие деталей + ограничение прав.
