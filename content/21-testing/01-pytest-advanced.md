В этом уроке мы разберём самый популярный в Python инструмент тестирования — **pytest**. Ты уже умеешь писать простые тесты, теперь научимся делать их по-настоящему мощными: готовить данные с помощью фикстур, прогонять один тест на десятках входных данных и перехватывать вывод программы.

## Тесты на обычном assert

Главное отличие pytest от unittest — никаких классов и особых методов. Тест — это просто функция, имя которой начинается с `test_`, а проверки записываются через встроенный `assert`:

```python
def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0
```

Сохрани код в файл `test_math.py` и запусти из той же папки:

```bash
python -m pytest
```

pytest сам найдёт файлы вида `test_*.py` и функции `test_*`. В конце ты увидишь сводку: `3 passed` (если тестов три) или `1 failed` с подробным diff — где ожидалось одно, а получилось другое. Заметь: внутри одного `assert` может быть сразу несколько проверок, и при падении pytest покажет значения обеих частей выражения.

## Фикстуры: готовим окружение

Когда у тестов есть общие данные (объект базы, временный файл, пользователь), не стоит копировать подготовку в каждый тест. Для этого в pytest есть **фикстуры** — функции с декоратором `@pytest.fixture`. Тест просто объявляет имя фикстуры параметром, и pytest сам вызовет её и передаст результат:

```python
import pytest

@pytest.fixture
def user():
    return {"name": "Аня", "age": 30}

def test_user(user):
    assert user["name"] == "Аня"
    assert user["age"] == 30
```

У фикстур есть параметр `scope` — область жизни:

- `function` — создаётся заново для каждого теста (по умолчанию);
- `class` — один раз на класс;
- `module` — один раз на весь файл;
- `session` — один раз на весь прогон.

Если фикстура тяжёлая (подключение к БД, загрузка большого файла), подними scope до `module` или `session`, чтобы не создавать ресурс сотни раз:

```python
@pytest.fixture(scope="module")
def db():
    return connect_to_database()
```

## Yield-фикстуры: настройка и очистка

Часто ресурс нужно не только создать, но и убрать после теста: закрыть соединение, удалить файл. Для этого в фикстуре используется `yield`: всё, что до `yield`, — настройка, а всё, что после, — очистка, которая выполнится после завершения теста:

```python
@pytest.fixture
def temp_file(tmp_path):
    f = tmp_path / "data.txt"
    f.write_text("hello")
    yield f
    f.unlink(missing_ok=True)
```

## Параметризация

Иногда нужно прогнать один и тот же тест на множестве входных данных. Писать десять отдельных тестов — скучно. На помощь приходит `@pytest.mark.parametrize`:

```python
@pytest.mark.parametrize("a,b,expected", [
    (1, 2, 3),
    (0, 0, 0),
    (-1, 1, 0),
])
def test_add_parametrized(a, b, expected):
    assert add(a, b) == expected
```

pytest превратит эту запись в три отдельных теста и покажет в отчёте входные данные. Если один из прогонов упадёт, остальные продолжат выполняться — ты сразу увидишь, на каких именно данных проблема.

## Встроенные фикстуры

У pytest есть готовые фикстуры: `tmp_path` — временная директория для каждого теста, `capsys` — перехват вывода `print()` и `sys.stdout`, `monkeypatch` — подмена объектов (о ней подробно в следующем уроке). Ещё бывают полезны маркеры: `@pytest.mark.skip` пропускает тест, `@pytest.mark.xfail` помечает ожидаемо падающий.

### Разбор 1
Решение:

```python
def multiply(a, b):
    return a * b

def test_multiply_positive():
    assert multiply(3, 4) == 12

def test_multiply_zero():
    assert multiply(5, 0) == 0

def test_multiply_float():
    assert multiply(1.5, 2) == 3.0
```

Запуск: `python -m pytest`. Результат: `3 passed`.

Что здесь происходит? pytest находит файл `test_math.py` по префиксу `test_`, затем собирает все функции, начинающиеся с `test_`, и запускает каждую по очереди. Функция `multiply` определена в том же файле, поэтому доступна тестам. Каждая проверка — это `assert`; если выражение ложно, pytest останавливает тест и показывает, какое значение ожидалось, а какое получилось. Обрати внимание: тесты независимы — если один упадёт, остальные всё равно выполнятся, и ты увидишь полную картину.

### Разбор 2
Решение:

```python
import pytest

def rect_area(width, height):
    return width * height

@pytest.mark.parametrize("width,height,expected", [
    (3, 4, 12),
    (0, 5, 0),
    (2.5, 4, 10.0),
])
def test_rect_area(width, height, expected):
    assert rect_area(width, height) == expected
```

Запуск: `python -m pytest`. Результат: `6 passed` (3 предыдущих + 3 параметризованных прогона).

Что здесь происходит? Декоратор `@pytest.mark.parametrize` получает строку с именами параметров и список кортежей значений. pytest разворачивает это в три отдельных теста, подставляя каждый кортеж в аргументы функции. В отчёте каждый прогон отображается отдельно: `test_rect_area[3-4-12]`, `test_rect_area[0-5-0]`, `test_rect_area[2.5-4-10.0]`. Если бы один из примеров был ошибочным, pytest показал бы именно его, и остальные продолжили бы работать — это главная ценность параметризации. Обрати внимание: в первой строке декоратора имена параметров разделены запятыми и должны точно совпадать с аргументами функции.

### Разбор 3
Решение:

```python
import pytest

@pytest.fixture
def users():
    return [
        {"name": "Иван", "active": False},
        {"name": "Аня", "active": True},
        {"name": "Пётр", "active": False},
    ]

def test_users(users):
    assert len(users) == 3
    assert users[1]["active"] is True
```

Запуск: `python -m pytest`. Результат: `1 passed`.

Что здесь происходит? pytest видит, что тест `test_users` объявляет параметр `users`, ищет фикстуру с таким именем и вызывает её перед тестом, передавая возвращённый список. Для каждого теста фикстура `function`-области создаётся заново — это гарантирует, что тесты не будут влиять на данные друг друга. Обрати внимание: с `bool` сравнивают через `is True`, а не `== True`, хотя оба варианта работают. Если фикстура понадобится нескольким файлам, её выносят в `conftest.py` — pytest подхватит её автоматически.

### Разбор 4
Решение:

```python
import pytest

@pytest.fixture
def log_file(tmp_path):
    f = tmp_path / "log.txt"
    f.write_text("started")
    yield f
    f.unlink(missing_ok=True)
    assert not f.exists()

def test_log_file(log_file):
    assert log_file.exists()
    assert log_file.read_text() == "started"
```

Запуск: `python -m pytest`. Результат: `1 passed`.

Что здесь происходит? Код до `yield` выполняется как настройка: создаётся файл в уникальной временной папке `tmp_path` и в него пишется строка. Тест получает путь `log_file` и проверяет, что файл существует и содержит нужный текст. После завершения теста управление возвращается в фикстуру уже после `yield`: файл удаляется, и `assert not f.exists()` подтверждает, что очистка сработала. Это классический шаблон «setup → тест → teardown». Если бы тест упал, очистка всё равно выполнилась бы — это важное преимущество yield-фикстур перед ручной очисткой в конце теста, которую можно просто не дойти.

### Разбор 5
Решение:

```python
def greet(name):
    print(f"Привет, {name}!")

def test_greet(capsys):
    greet("Аня")
    captured = capsys.readouterr()
    assert captured.out == "Привет, Аня!\n"
```

Запуск: `python -m pytest`. Результат: `1 passed`.

Что здесь происходит? Фикстура `capsys` перехватывает весь вывод `print()` и `sys.stdout` во время теста. После вызова `greet("Аня")` мы читаем захваченный вывод через `capsys.readouterr()` — он возвращает объект с атрибутами `out` (обычный вывод) и `err` (вывод в stderr). Сравниваем `captured.out` с ожидаемой строкой. Обрати внимание на `\n` в конце: `print()` добавляет перенос строки автоматически, поэтому ожидаемая строка должна его содержать. Такая проверка полезна для функций, которые не возвращают значение, а печатают результат, — например, для CLI-утилит.
