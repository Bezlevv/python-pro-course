Тесты есть — но сколько кода они проверяют? Непроверенные строки могут скрывать серьёзные баги. В этом уроке научимся измерять **покрытие** (coverage) и встраивать тесты в непрерывную интеграцию (CI), чтобы качество проверялось автоматически при каждом изменении кода.

## Что такое покрытие

Покрытие — это процент строк кода, которые были выполнены хотя бы раз во время прогона тестов. Если в модуле 100 строк, а тесты выполнили 75, покрытие — 75%. Логика простая: код, который никогда не выполнялся, не проверен — в нём могут жить ошибки.

Важно понимать ограничения: покрытие говорит лишь о том, что строка *выполнялась*, а не о том, что её результат *проверялся*. 100% покрытия не гарантирует отсутствие багов, но низкое покрытие — верный сигнал о дырах в тестах.

## pytest-cov: считаем покрытие

Инструмент — пакет `pytest-cov`. Установка:

```bash
pip install pytest-cov
```

Запуск с измерением покрытия модуля `calc`:

```bash
python -m pytest --cov=calc --cov-report=term-missing
```

Что мы увидим:

- `Stmts` — количество исполняемых строк;
- `Miss` — непокрытые строки;
- `Cover` — процент покрытия;
- колонку `Missing` — номера строк, которые не были выполнены.

Флаг `--cov-report=term-missing` добавляет колонку `Missing`. Есть и другие форматы отчётов: `html`, `xml` (удобно для CI), `json`.

## Порог качества

Мало измерить — стоит задать минимальный порог. Если покрытие упадёт ниже, CI должен остановить сборку:

```bash
python -m pytest --cov=calc --cov-fail-under=80
```

Если покрытие окажется меньше 80%, pytest завершится с ошибкой. Порог — это дисциплина команды: чем ответственнее проект, тем выше порог.

## Покрытие веток

По умолчанию считается покрытие строк. Но можно измерять и покрытие **веток** (`if`/`else`, тернарных операторов). Ветка считается покрытой, если выполнялись обе её ветви:

```bash
python -m pytest --cov=calc --cov-branch --cov-report=term-missing
```

Без `--cov-branch` код, где `if` всегда истинен, покажет 100% строка — но ветка `else` так и останется неиспытанной.

## Исключение строк

Не весь код нужно покрывать: например, блок `if __name__ == "__main__":` — это точка входа, которая не тестируется. Её можно исключить из подсчёта:

```python
if __name__ == "__main__":
    main()  # pragma: no cover
```

Комментарий `# pragma: no cover` говорит coverage-инструменту пропустить строку. Также можно исключить целые файлы через конфигурационный файл `.coveragerc`.

## Интеграция с CI

CI (Continuous Integration) — практика автоматического запуска проверок при каждом изменении кода. Самый частый инструмент — GitHub Actions. Workflow описывается YAML-файлом `.github/workflows/ci.yml`:

```yaml
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pytest pytest-cov
      - run: python -m pytest --cov=calc --cov-fail-under=80
```

Каждый push в репозиторий запустит джобу `test`: клонирует код, установит Python, поставит зависимости и прогонит тесты с порогом покрытия. Если тест упадёт или покрытие будет ниже порога — CI пометится красным, и команда узнает о проблеме раньше, чем пользователь.

### Разбор 1
Решение:

```python
# calc.py
def add(a, b):
    return a + b

def subtract(a, b):
    return a - b
```

```python
# test_calc.py
from calc import add

def test_add():
    assert add(2, 3) == 5
```

Запуск: `python -m pytest --cov=calc --cov-report=term-missing`. Результат: покрытие около 50%, в `Missing` — строка `subtract` (например, `5`).

Что здесь происходит? Покрытие считается по строкам, которые реально выполнились во время тестов. Тест вызывает только `add`, поэтому строка с `subtract` никогда не выполнялась и попала в `Missing`. Отчёт показывает: `Stmts` — сколько исполняемых строк в модуле, `Miss` — сколько не покрыто, `Cover` — процент. Колонка `Missing` — самое ценное: она говорит, какие именно строки не проверены. Теперь мы видим дыру: `subtract` не тестирована.

### Разбор 2
Решение:

```python
# test_calc.py
from calc import add, subtract

def test_add():
    assert add(2, 3) == 5

def test_subtract():
    assert subtract(10, 4) == 6
```

Запуск: `python -m pytest --cov=calc --cov-report=term-missing --cov-fail-under=100`. Результат: `Cover` — 100%, `Missing` пуст, прогон успешен.

Что здесь происходит? Добавлен тест для `subtract`, и теперь обе функции выполнились. Покрытие достигло 100%, `Missing` пуст. Флаг `--cov-fail-under=100` добавляет жёсткое требование: если покрытие окажется ниже 100%, pytest завершится с ошибкой — именно так пороги работают в CI. Обрати внимание: 100% здесь достижимо, потому что модуль маленький. В реальных проектах порог обычно 70–90%, потому что стопроцентное покрытие не всегда оправдано экономически.

### Разбор 3
Решение:

```python
# calc.py
def sign(x):
    if x < 0:
        return -1
    if x > 0:
        return 1
    return 0
```

```python
# test_calc.py
from calc import sign

def test_sign_negative():
    assert sign(-5) == -1

def test_sign_positive():
    assert sign(5) == 1

def test_sign_zero():
    assert sign(0) == 0
```

Запуск: `python -m pytest --cov=calc --cov-branch --cov-report=term-missing`. Результат: покрытие веток 100%.

Что здесь происходит? Без `--cov-branch` хватило бы одного теста (например, `sign(5) == 1`) — строка выполнилась бы. Но ветки `x < 0` и `x == 0` остались бы неиспытанными. С флагом `--cov-branch` инструмент следит за обеими ветвями каждого условия: чтобы ветка была покрыта, должны выполниться обе её стороны. Три теста — отрицательное, положительное и ноль — покрывают все ветки, и отчёт показывает 100% веток. Это важная практика: многие баги живут именно в ветках, которые «никогда не случаются».

### Разбор 4
Решение:

```python
# calc.py
def add(a, b):
    return a + b

def subtract(a, b):
    return a - b

if __name__ == "__main__":
    print(add(2, 3))  # pragma: no cover
```

Запуск: `python -m pytest --cov=calc --cov-report=term-missing --cov-fail-under=100`. Результат: `Cover` — 100%, без `Missing`.

Что здесь происходит? Блок `if __name__ == "__main__":` — стандартный способ дать модулю точку входа, но тесты его не запускают, поэтому строки попадали бы в `Missing`. Комментарий `# pragma: no cover` говорит coverage-инструменту исключить строку из подсчёта. Внимание: в решении выше комментарий стоит только на `print` — но строка `if` тоже подлежит исключению, поэтому в полном решении нужно пометить обе строки:

```python
if __name__ == "__main__":  # pragma: no cover
    print(add(2, 3))  # pragma: no cover
```

Так точка входа не «портит» покрытие. Это честный приём: блок, который не предназначен для тестирования, явно помечается.

### Разбор 5
Решение — файл `.github/workflows/ci.yml`:

```yaml
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pytest pytest-cov
      - run: python -m pytest --cov=calc --cov-fail-under=90
```

Что здесь происходит? При каждом `push` и `pull_request` GitHub создаст виртуальную машину с Ubuntu, выполнит шаги по порядку: склонирует репозиторий (`checkout`), поставит Python 3.12 (`setup-python`), установит pytest и pytest-cov, затем прогонит тесты с порогом покрытия 90%. Если тест упадёт или покрытие окажется ниже 90%, джоба завершится с ошибкой, и в GitHub появится красная галочка. Это и есть CI: все проверки выполняются автоматически при каждом изменении, и команда сразу видит, что код здоров, а покрытие — в норме.
