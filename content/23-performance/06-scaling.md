Когда сервис перестаёт успевать обрабатывать запросы, возникает вопрос масштабирования. Урок объясняет, как думать о производительности сервиса: от метрик задержек до очередей фоновых задач, кэширования и числа экземпляров.

## Вертикальное и горизонтальное масштабирование

**Вертикальное** — сделать одну машину мощнее: больше ядер, памяти, диск быстрее. Просто, но есть предел: самый мощный сервер стоит дорого, а отказ одной машины — простой сервиса.

**Горизонтальное** — добавить больше одинаковых машин (инстансов) и распределять нагрузку между ними. Масштабируется почти безгранично и повышает отказоустойчивость. Главное условие: сервис должен быть **stateless** — не хранить состояние запроса на инстансе; иначе запросы, ушедшие на разные инстансы, будут видеть разные данные. Если состояние нужно (сессия, кэш), его выносят в общее хранилище: базу данных, Redis, shared-кэш.

## Воркеры: сколько процессов

Веб-сервер на Python обычно запускает несколько процессов-воркеров. Нагруженный CPU-код не ускоряется потоками из-за GIL, поэтому стандартная схема — один воркер на ядро. Например, для FastAPI + uvicorn:

```bash
uvicorn app:app --workers 4
```

А для синхронных приложений — gunicorn:

```bash
gunicorn app:app --workers 4 --threads 2
```

Правило-ориентир: `workers = 2 * CPU_cores + 1` для gunicorn, но для Python чаще берут количество ядер. Увеличивать число воркеров вслепую не стоит: каждый процесс — своя память и своё соединение с базой данных, и избыток воркеров упирается в ресурсы.

## Очереди и фоновые задачи

Тяжёлую работу (отправка писем, генерация отчётов, обработка картинок) не делают прямо в запросе — её кладут в очередь, а воркеры-потребители берут задачи оттуда. Это сглаживает пики: пользователь получает ответ мгновенно, а работа выполняется фоном.

Минимальная демонстрация очереди со стандартной библиотекой:

```python
import queue
import threading
import time

job_queue = queue.Queue()
results = []
lock = threading.Lock()

def worker():
    while True:
        item = job_queue.get()
        if item is None:
            break
        time.sleep(0.05)          # имитация работы
        with lock:
            results.append(item * 2)
        job_queue.task_done()

for _ in range(4):
    threading.Thread(target=worker, daemon=True).start()

for i in range(20):
    job_queue.put(i)

job_queue.join()
print(sorted(results))
```

`queue.Queue` потокобезопасна; `task_done()`/`join()` позволяют дождаться обработки всех задач.

## Кэширование

Повторные одинаковые запросы не обязаны считаться заново. Встроенный `functools.lru_cache` памят запоминает результаты вызовов функции:

```python
from functools import lru_cache
import time

@lru_cache(maxsize=128)
def compute_report(key):
    time.sleep(0.1)               # дорогой расчёт
    return f"report-{key}"

t0 = time.perf_counter()
compute_report("monthly")
t1 = time.perf_counter()
compute_report("monthly")          # из кэша
t2 = time.perf_counter()
print(f"первый вызов: {t1 - t0:.3f} сек")
print(f"повторный вызов: {t2 - t1:.3f} сек")
print(compute_report.cache_info())
```

`cache_info()` показывает `hits`, `misses`, `maxsize`, `currsize`. В распределённой системе кэш выносят в общий сервис (например, Redis), чтобы он был одинаковым для всех инстансов.

## Метрики: p50, p95, p99

Среднее время ответа обманчиво: один медленный запрос «портит» среднее. Поэтому используют перцентили: **p95** означает «95% запросов уложились в это время». p95 — стандарт для целей по задержке:

```python
import math
import random

latencies = sorted(random.expovariate(1 / 0.05) for _ in range(1000))

def percentile(sorted_values, p):
    k = (len(sorted_values) - 1) * p
    f = math.floor(k)
    c = math.ceil(k)
    if f == c:
        return sorted_values[f]
    return sorted_values[f] + (sorted_values[c] - sorted_values[f]) * (k - f)

print(f"p50: {percentile(latencies, 0.5):.4f} сек")
print(f"p95: {percentile(latencies, 0.95):.4f} сек")
```

## Ретраи и backoff

Сетевые ошибки случаются. Типовая практика — повторить запрос с экспоненциальной паузой (backoff):

```python
import time
import random

def flaky_call(attempt):
    if random.random() < 0.6:
        raise ConnectionError("временный сбой")
    return "ok"

def with_retry(func, attempts=5, base_delay=0.1):
    for attempt in range(1, attempts + 1):
        try:
            return func(attempt)
        except ConnectionError:
            if attempt == attempts:
                raise
            time.sleep(base_delay * 2 ** (attempt - 1))

print(with_retry(flaky_call))
```

## Оценка числа инстансов

Когда известны p95, ёмкость одного инстанса и целевой трафик, число инстансов вычисляется просто:

```python
target_rps = 10_000          # целевой трафик
instance_capacity = 1_000    # запросов в секунду на один инстанс
instances = math.ceil(target_rps / instance_capacity)
print(f"нужно инстансов: {instances}")
```

В реальности добавляют запас на пики и отказы (например, ×1.5) и делают автоскейлинг по метрикам.
