API — это контракт между клиентом и сервером. Если контракт плохо спроектирован, каждое изменение сервера что-то ломает у клиентов. Разберём два главных подхода — REST и GraphQL — и правила версионирования.

## REST: ресурсы и методы

REST строит API вокруг **ресурсов** — существительных (`/users`, `/orders`) — и стандартных методов HTTP. Каждый метод несёт смысл: `GET` читает, `POST` создаёт, `PUT` полностью заменяет, `PATCH` частично обновляет, `DELETE` удаляет. Статус-коды сигнализируют о результате: `200` для успеха, `201` для созданного ресурса, `400` для неверного запроса клиента, `401/403` для проблем с правами, `404` для отсутствующего ресурса, `429` для превышения лимитов, `5xx` для ошибок сервера.

Вот минимальный CRUD на FastAPI:

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()
books = {}

class Book(BaseModel):
    id: int
    title: str
    author: str

@app.post("/books", status_code=201)
def create_book(book: Book):
    books[book.id] = book
    return book

@app.get("/books/{book_id}")
def get_book(book_id: int):
    if book_id not in books:
        raise HTTPException(status_code=404, detail="Книга не найдена")
    return books[book_id]

@app.delete("/books/{book_id}", status_code=204)
def delete_book(book_id: int):
    books.pop(book_id, None)
```

Обрати внимание на идемпотентность: `GET`, `PUT`, `DELETE` можно безопасно повторять — повторный `DELETE` не ломает состояние. `POST` идемпотентным не считается, поэтому повторы `POST` могут создавать дубликаты (об этом — в уроке про идемпотентность).

## GraphQL: один endpoint, схема и запросы

GraphQL отдаёт клиенту **схему** (schema) — описание типов и возможных операций. Клиент запрашивает ровно те поля, которые нужны, одним запросом на единственный endpoint `/graphql`. Схема строится на типах:

```graphql
type Book {
  id: ID!
  title: String!
  author: Author!
}

type Author {
  id: ID!
  name: String!
  books: [Book!]!
}

type Query {
  book(id: ID!): Book
  books: [Book!]!
}
```

Запрос выбирает поля:

```graphql
query {
  book(id: 1) {
    title
    author {
      name
    }
  }
}
```

Главные плюсы GraphQL: клиент сам решает, какие поля получать (нет «лишних данных» и «недостающих»), один запрос объединяет несколько ресурсов, схема документирует API. Минусы: сложнее кэшировать (нет URL-адресов как адресов кэша), сложнее ограничивать нагрузку (глубокие вложенные запросы), выше порог входа.

## Когда что выбирать

REST хорош для большинства публичных API: простые ресурсы, кэширование через HTTP, знакомая семантика. GraphQL оправдан, когда много разных клиентов с разными потребностями в данных (мобильные приложения, виджеты), когда нужно агрегировать несколько сервисов одним запросом и когда важна точная выборка полей. Признак переусложнения: если у тебя один клиент и простые ресурсы — GraphQL чаще всего избыточен.

## Версионирование API

Коденты наверняка есть в продакшене, поэтому ломающие изменения нужно вводить так, чтобы старые клиенты не перестали работать. Основные стратегии:

1. **URI-версии**: `/v1/users` и `/v2/users` — самые явные и распространённые; старый адрес продолжает жить.
2. **Заголовок Accept**: клиент просит `application/vnd.api+json;version=2` — версия не засоряет URL, но менее наглядна.
3. **Непрерывная эволюция**: добавляем поля и методы, не удаляя старые; удаляем только после согласования с владельцами клиентов.

Правило простое: **неразрывные изменения (новая опция, новое поле) добавляй без версии, ломающие — через версию**. И всегда документируй, что изменено в каждой версии.

### Разбор 1
Пример таблицы:

| Метод | Путь | Статус при успехе | Назначение |
|---|---|---|---|
| POST | `/posts` | 201 | Создать пост |
| GET | `/posts` | 200 | Список постов |
| GET | `/posts/{id}` | 200 | Один пост |
| GET | `/posts/{id}/comments` | 200 | Комментарии поста |
| POST | `/posts/{id}/comments` | 201 | Добавить комментарий |
| DELETE | `/comments/{id}` | 204 | Удалить комментарий |

Что здесь происходит? Комментарии — вложенный ресурс, поэтому их путь начинается с `/posts/{id}`. Удаление возвращает 204 без тела ответа. Такая таблица — это и есть контракт: клиент видит все операции и ожидаемые статусы, а сервер обязуется им следовать.

### Разбор 2
Решение:

```python
def status_for(operation):
    codes = {
        "create": 201,
        "read": 200,
        "delete": 204,
        "invalid": 400,
        "not_found": 404,
        "forbidden": 403,
    }
    return codes.get(operation, 500)

for op in ["create", "read", "delete", "invalid", "not_found", "forbidden"]:
    print(f"{op} -> {status_for(op)}")
```

Вывод:

```
create -> 201
read -> 200
delete -> 204
invalid -> 400
not_found -> 404
forbidden -> 403
```

Что здесь происходит? Неизвестная операция получает 500 — так мы явно показываем, что не знаем, как её обработать. Статус-коды — часть контракта, поэтому важно, чтобы одна и та же ошибка всегда имела один код.

### Разбор 3
Решение:

```python
from pydantic import BaseModel

class Book(BaseModel):
    id: int
    title: str
    author: str

books = {}

def create_book(book):
    books[book.id] = book
    return 201

def get_book(book_id):
    return books.get(book_id)

print(create_book(Book(id=1, title="Война и мир", author="Толстой")))
print(get_book(1).title)
print(404 if get_book(999) is None else 200)
```

Вывод:

```
201
Война и мир
404
```

Что здесь происходит? Функции имитируют поведение эндпоинтов: создание возвращает 201, чтение существующей книги — её данные, отсутствующей — 404. В настоящем FastAPI вместо печати кода использовались бы `status_code=201` и `HTTPException(status_code=404)`.

### Разбор 4
Схема:

```graphql
type Product {
  id: ID!
  name: String!
  price: Float!
}

type Category {
  id: ID!
  name: String!
  products: [Product!]!
}

type Query {
  product(id: ID!): Product
  products: [Product!]!
  category(id: ID!): Category
}
```

Запросы:

```graphql
query {
  product(id: 1) {
    name
    price
  }
}

query {
  category(id: 2) {
    name
    products {
      name
    }
  }
}
```

Что здесь происходит? Схема — контракт GraphQL: клиент видит все типы и связи. Поле `products` внутри `Category` позволяет получить товары категории без отдельных запросов. В первом запросе берём только имя и цену товара, во втором — имя категории и имена её товаров.

### Разбор 5
Разделение `name` на `first_name` и `last_name` — ломающее изменение: клиенты v1 читают поле `name`, и его исчезновение сломает их парсинг. План: v1 продолжает работать без изменений — сервер склеивает `first_name` и `last_name` в `name` для старого формата; v2 отдаёт новые поля; параллельно уведомляем владельцев клиентов, даём им время перейти на v2, и только когда трафик v1 станет нулевым, выключаем v1. Непрерывная эволюция здесь невозможна, потому что старое поле исчезает.

```json
{
  "id": 7,
  "first_name": "Лев",
  "last_name": "Толстой",
  "email": "leo@example.com"
}
```

Что здесь происходит? Версия в URI делает сосуществование контрактов очевидным: `/v1/users/{id}` и `/v2/users/{id}` живут рядом, пока старые клиенты не мигрируют.
