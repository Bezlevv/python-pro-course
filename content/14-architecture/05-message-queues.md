Очередь сообщений — это буфер между производителем (producer) и потребителем (consumer). Производитель кладёт сообщение в очередь, а потребитель достаёт и обрабатывает. Главная выгода — **слабая связанность**: производитель не знает, кто и когда обработает сообщение, и не ждёт ответа. Это позволяет разносить пики нагрузки, переживать простои потребителей и масштабировать обработчики независимо.

## Рабочая очередь

Самая простая модель: несколько потребителей соревнуются за сообщения — каждое сообщение получает ровно один потребитель (competing consumers). Классический пример — отправка писем или обработка изображений: продюсер публикует задачи, воркеры разбирают их параллельно.

В Python можно показать идею на стандартной `queue.Queue` с потоками:

```python
import threading
import queue
import time

jobs = queue.Queue()
for i in range(5):
    jobs.put(f"задача {i}")

def worker(worker_id):
    while not jobs.empty():
        try:
            job = jobs.get_nowait()
        except queue.Empty:
            return
        print(f"Воркер {worker_id} взял: {job}")
        time.sleep(0.1)
        jobs.task_done()

threads = [threading.Thread(target=worker, args=(n,)) for n in (1, 2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

Здесь уже видна суть рабочей очереди: задачи распределяются между потоками, и каждый потребитель берёт следующую свободную.

## Брокеры: RabbitMQ и Kafka

В реальных системах очередь живёт в **брокере** — отдельном сервисе. RabbitMQ — классический брокер с поддержкой моделей обмена: прямые очереди, обменники (exchanges) с роутингом, pub/sub. Kafka — распределённый журнал (log): сообщения хранятся как поток событий, потребители читают их со своей скоростью, могут перечитывать историю. Kafka идеален для событийных шин и аналитики, RabbitMQ — для задач и рабочих очередей.

Пример отправки в RabbitMQ через библиотеку `pika` (установка `pip install pika`):

```python
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()
channel.queue_declare(queue="tasks")
channel.basic_publish(exchange="", routing_key="tasks", body="Привет, очередь!")
connection.close()
```

## Pub/Sub

В модели pub/sub сообщение получают **все** подписчики топика, а не один. Это нужно для событий: «заказ создан» должны услышать и склад, и аналитика, и уведомления. В RabbitMQ для этого используются обменники типа `fanout` или `topic`, а топики Kafka работают на том же принципе.

## Гарантии доставки

Гарантии — важнейшая тема очередей:

- **At-most-once**: сообщение может потеряться (без подтверждений).
- **At-least-once**: сообщение будет доставлено, но возможно несколько раз — получатель должен быть идемпотентным.
- **Exactly-once**: ровно один раз — реализуется комбинацией механизмов, всегда дорого и не всегда достижимо.

На практике стандарт — at-least-once + идемпотентный обработчик: повторные доставки безопасны, потому что обработчик умеет распознавать дубликаты (по id сообщения).

## Мёртвые письма и retry

Если обработка падает, сообщение нельзя терять. Стратегия — **retry с backoff**: повторять с нарастающей задержкой, а после N попыток класть сообщение в **dead-letter очередь** (очередь мёртвых писем) для ручного разбора. Это как в микросервисах с circuit breaker, только на уровне сообщений.

## Идемпотентность потребителя

Потребитель должен обрабатывать одно и то же сообщение дважды без вреда. Простой приём — запоминать ID обработанных сообщений:

```python
processed = set()

def handle(message):
    if message["id"] in processed:
        return
    processed.add(message["id"])
    print(f"Обработано: {message['id']}")
```

### Разбор 1
Решение:

```python
import threading
import queue
import time

jobs = queue.Queue()
for i in range(1, 7):
    jobs.put(i)

def worker(worker_id):
    while True:
        try:
            job = jobs.get_nowait()
        except queue.Empty:
            return
        print(f"Воркер {worker_id} взял: {job}")
        time.sleep(0.05)
        jobs.task_done()

threads = [threading.Thread(target=worker, args=(n,)) for n in (1, 2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

Пример вывода:

```
Воркер 1 взял: 1
Воркер 2 взял: 2
Воркер 1 взял: 3
Воркер 2 взял: 4
Воркер 1 взял: 5
Воркер 2 взял: 6
```

Что здесь происходит? `queue.Queue` потокобезопасна: потоки конкурируют за задачи, и каждая задача достаётся ровно одному воркеру. `task_done()` сообщает очереди, что задача обработана, — это пригодится в пятой задаче для `join()`.

### Разбор 2
Решение:

```python
import time

def always_fails(job):
    raise RuntimeError("сбой")

def process_with_retry(job, attempts=3, base_delay=0.05):
    for attempt in range(attempts):
        try:
            always_fails(job)
            return (True, job)
        except Exception:
            if attempt == attempts - 1:
                return (False, job)
            time.sleep(base_delay * 2 ** attempt)

job = {"id": 1}
success, job = process_with_retry(job)
print(f"Мёртвое письмо: {job}" if not success else "Успех")
```

Вывод: `Мёртвое письмо: {'id': 1}`. Что здесь происходит? Функция делает три попытки с задержками 0.05 c, 0.1 c и 0.2 c. Так как `always_fails` всегда бросает исключение, после третьей попытки возвращается `(False, job)` — признак мёртвого письма. В реальной системе такое сообщение перекладывается в отдельную очередь для ручного анализа, а не теряется.

### Разбор 3
Решение:

```python
class IdempotentConsumer:
    def __init__(self):
        self.processed = set()

    def process(self, message):
        if message["id"] in self.processed:
            print(f"Дубликат: {message['id']}")
            return
        self.processed.add(message["id"])
        print(f"Обработано: {message['id']}")

consumer = IdempotentConsumer()
consumer.process({"id": 1})
consumer.process({"id": 1})
consumer.process({"id": 2})
```

Вывод:

```
Обработано: 1
Дубликат: 1
Обработано: 2
```

Что здесь происходит? Множество `processed` хранит ID уже обработанных сообщений. Повторная доставка сообщения с id=1 распознаётся и игнорируется — это и есть идемпотентность, ключ к безопасному режиму at-least-once.

### Разбор 4
Решение:

```python
class Broker:
    def __init__(self):
        self.subscribers = {}

    def subscribe(self, topic, callback):
        self.subscribers.setdefault(topic, []).append(callback)

    def publish(self, topic, message):
        for callback in self.subscribers.get(topic, []):
            callback(message)

broker = Broker()
broker.subscribe("order.created", lambda m: print(f"Склад получил: {m['order_id']}"))
broker.subscribe("order.created", lambda m: print(f"Аналитика получила: {m['order_id']}"))

broker.publish("order.created", {"order_id": 7})
broker.publish("other.topic", {"order_id": 999})
```

Вывод:

```
Склад получил: 7
Аналитика получила: 7
```

Что здесь происходит? В pub/sub каждый подписчик топика получает каждое сообщение. Публикация в незанятый топик не вызывает никаких колбэков, потому что список подписчиков пуст. Это минимальный, но полностью работающий брокер для понимания идеи.

### Разбор 5
Решение:

```python
import threading
import queue

jobs = queue.Queue()
for i in range(4):
    jobs.put(i)

def worker(worker_id):
    while True:
        try:
            job = jobs.get_nowait()
        except queue.Empty:
            return
        print(f"Готово: {job}")
        jobs.task_done()

threads = [threading.Thread(target=worker, args=(n,)) for n in (1, 2)]
for t in threads:
    t.start()

jobs.join()
print("Все задачи выполнены")
```

Вывод (порядок может отличаться):

```
Готово: 0
Готово: 1
Готово: 2
Готово: 3
Все задачи выполнены
```

Что здесь происходит? `jobs.join()` блокирует главную программу, пока не будут обработаны все задачи (каждая `task_done()` уменьшает счётчик). Только когда очередь опустела и все потоки закончили, печатается `Все задачи выполнены`. Это гарантирует, что завершение программы не произойдёт раньше, чем закончена обработка.
