Программа «не работает» — это нормальный этап разработки. Вопрос в том, как быстро понять, почему. Два главных инструмента зрелого разработчика — это **отладчик** (debugger) и **профилировщик** (profiler). Первый отвечает на вопрос «что происходит внутри программы?», второй — «где она тратит время?». Сегодня научимся пользоваться обоими.

## Отладка с pdb

`pdb` — встроенная в Python библиотека отладки. Чтобы остановить программу в нужном месте, вставь вызов `breakpoint()` (это сокращение для `pdb.set_trace()`):

```python
def factorial(n: int) -> int:
    if n == 0:
        return 1
    return n * factorial(n - 1)


breakpoint()  # здесь выполнение остановится
print(factorial(5))
```

Когда программа дойдёт до `breakpoint()`, ты попадёшь в интерактивную оболочку отладчика (приглашение `(Pdb)`). Главные команды:

| Команда | Что делает |
|---|---|
| `n` | next — перейти к следующей строке (не заходя внутрь функций) |
| `s` | step — войти внутрь текущей функции |
| `c` | continue — продолжить выполнение до следующей точки останова |
| `p <выражение>` | print — напечатать значение, например `p n` |
| `l` | list — показать текущий фрагмент кода |
| `w` | where — показать стек вызовов |
| `q` | quit — завершить отладку |

Что важнее всего — в любой момент можно посмотреть значения переменных и даже поменять их. Полезно также понимать, что `breakpoint()` проще, чем ручная установка отладчика из IDE: она работает везде, где запускается Python.

Если программа упала с исключением, к отладчику можно подключиться **после** падения — это называется post-mortem отладка. У себя в коде напиши:

```python
try:
    factorial(-5)
except Exception:
    import pdb
    pdb.pm()  # раскрывает контекст именно в месте ошибки
```

## Профилирование с cProfile

Когда программа работает, но медленно, нужен профилировщик — он помогает узнать, какая функция съедает больше всего времени. Самый простой способ запустить его — из командной строки:

```bash
python -m cProfile -s cumtime script.py
```

Ключ `-s cumtime` сортирует вывод по суммарному времени (см. ниже). Для примера создадим `slow.py`:

```python
def is_prime(n: int) -> bool:
    if n < 2:
        return False
    for d in range(2, n):
        if n % d == 0:
            return False
    return True


def count_primes(n: int) -> int:
    return sum(1 for x in range(2, n + 1) if is_prime(x))


if __name__ == "__main__":
    print(count_primes(10000))
```

Запусти профилировщик:

```bash
python -m cProfile -s cumtime slow.py
```

В выводе появится таблица. Ключевые колонки:

- `ncalls` — сколько раз вызывалась функция;
- `tottime` — время, проведённое **внутри самой функции** (без вложенных вызовов);
- `cumtime` — суммарное время с учётом всех вложенных вызовов.

Именно по `cumtime` обычно судят о «горячих точках»: строка с наибольшим значением — главный кандидат на оптимизацию. Профилирование можно запускать и из кода через `cProfile.Profile()` и `pstats`, но для начала хватит командной строки.

Для микро-замеров отдельных кусочков кода удобнее встроенный модуль `timeit`: он корректно учитывает разогрев и повторяет измерение много раз, чтобы сгладить случайные колебания.

```python
import timeit

print(timeit.timeit("'-'.join(str(n) for n in range(100))", number=10000))
```

### Разбор 1
Одно из возможных решений.

Шаг 1. Файл с `breakpoint()`:

```python
def is_prime(n: int) -> bool:
    if n < 2:
        return False
    for d in range(2, n):
        if n % d == 0:
            return False
    return True


def count_primes(n: int) -> int:
    return sum(1 for x in range(2, n + 1) if is_prime(x))


if __name__ == "__main__":
    breakpoint()
    print(count_primes(50))
```

В отладчике смотри: `n`, `p n`, `w`. `w` покажет стек вызовов — ты увидишь, что `count_primes` вызвана из `__main__`, а `is_prime` вызывается из `count_primes`. После разведки введи `q`.

Шаг 2. Команда:

```bash
python -m cProfile -s cumtime primes.py
```

Вывод будет примерно таким (цифры зависят от машины):

```
         9999 function calls in 0.041 seconds

   Ordered by: cumulative time

   ncalls  tottime  cumtime  percall  filename:lineno(function)
        1    0.000    0.041    0.041  primes.py:15(<module>)
        1    0.000    0.041    0.041  primes.py:10(count_primes)
     9998    0.041    0.041    0.000  primes.py:1(is_prime)
```

Самая «горячая» функция — `is_prime`: 9998 вызовов и фактически всё время программы. `count_primes` — тонкая обёртка: она сама почти ничего не делает, зато генерирует почти десять тысяч вызовов `is_prime`. Именно `is_prime` — кандидат на оптимизацию: достаточно сократить перебор делителей до `int(n ** 0.5) + 1`, и программа ускорится в разы. Это и есть типичный цикл работы: нашёл горячую точку профилировщиком, переписал алгоритм, повторил замер, убедился, что стало быстрее.

### Разбор 2
Решение:

```python
def divide(a: int, b: int) -> float:
    return a / b


def main() -> None:
    try:
        divide(10, 0)
    except ZeroDivisionError:
        print("Нельзя делить на ноль")

Сначала же, на этапе изучения, `pdb.pm()` открывал контекст: `p a` показывал аргументы (`a = 10`), а `w` — стек, где видно, что исключение возникло в `divide`, вызванной из `main`. Post-mortem ценен тем, что не требует заранее ставить точку останова: ты попадаешь в сам момент падения и можешь осмотреть переменные в том самом кадре стека.

### Разбор 3
Решение:

```python
import timeit

setup = "nums = list(range(1000))"

ways = {
    "join + map": '",".join(map(str, nums))',
    "join + генератор": '",".join(str(n) for n in nums)',
    "цикл +=": (
        "out = ''\n"
        "for n in nums:\n"
        "    out += str(n) + ','\n"
        "out[:-1]"
    ),
}

for name, stmt in ways.items():
    times = timeit.repeat(stmt, setup=setup, number=10, repeat=5)
    print(f"{name}: {min(times):.4f} с")
```

`timeit.repeat` повторяет замер `repeat` раз и возвращает список времён; минимальное значение — самое честное, оно меньше зависит от посторонней нагрузки. Первый способ собирает строку через C-уровневый `join` без промежуточных объектов. Второй делает то же, но с генератором — чуть медленнее из-за накладных расходов на итерацию. Третий — цикл с `+=` — самый медленный: строки в Python неизменяемы, каждая операция `+=` создаёт новую строку и копирует в неё всё старое содержимое, поэтому суммарная работа растёт квадратично с длиной результата.

### Разбор 4
Решение:

```python
import time


def is_prime_naive(n: int) -> bool:
    if n < 2:
        return False
    for d in range(2, n):
        if n % d == 0:
            return False
    return True


def is_prime_sqrt(n: int) -> bool:
    if n < 2:
        return False
    for d in range(2, int(n ** 0.5) + 1):
        if n % d == 0:
            return False
    return True


def count_primes(n: int, is_prime_func) -> int:
    return sum(1 for x in range(2, n + 1) if is_prime_func(x))


n = 100_000
for name, func in [("наивная", is_prime_naive), ("с sqrt", is_prime_sqrt)]:
    start = time.perf_counter()
    result = count_primes(n, func)
    elapsed = time.perf_counter() - start
    print(f"count_primes({n}) = {result}, {name}: {elapsed:.4f} с")
```

Наивная версия в худшем случае проверяет до n-1 делителей для каждого числа: всего ~n·n = 10¹⁰ операций, что занимает секунды. Версия с sqrt проверяет не больше √n делителей: для n=100000 это ~316 проверок на число, суммарно ~n·√n ≈ 3,16·10⁷ — в сотни раз меньше. Отсюда и разница во времени. Количество найденных простых одинаково: 9592 — значит, результат не изменился, изменилась только скорость. Это классический пример: профилировщик показал «горячую точку», и оптимизация алгоритма (а не микро-правки) дала главный выигрыш.

### Разбор 5
Решение:

```python
def average_grades(grades: list[int]) -> float:
    total = 0
    for i in range(len(grades)):
        total += grades[i]
    return total / len(grades)


print(average_grades([3, 4, 5]))
```

Отладка по шагам: поставив `breakpoint()` в начало цикла, шагаем командой `n` и смотрим `p total`. На первом шаге `total` становится 4 вместо 3 — сразу видно, что прибавляется не `grades[i]`, а `grades[i] + 1`. Лишняя единица была внесена намеренно; после её удаления сумма равна 12, а деление на 3 даёт 4.0. Этот разбор показывает главный навык: не «смотреть глазами» на код, а шагать по нему и наблюдать значения в конкретные моменты. Проверочные данные подтверждают исправление: `(3 + 4 + 5) / 3 = 4.0`.

* Правильный ответ: Вызвать `pdb.pm()` в блоке `except`

- Только время самой функции, без вложенных вызовов
