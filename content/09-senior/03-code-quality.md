В одиночку ты можешь читать свой код даже очень небрежный. Но в команде, через месяц, «грязный» код превращается в источник ошибок и траты времени. Поэтому индустрия давно выработала набор инструментов, которые проверяют код автоматически: **линтеры** (ищут ошибки и плохие практики), **форматтеры** (приводят оформление к единому стилю), **проверщики типов** (ловят несоответствия аннотациям) и **хуки** (запускают всё это автоматически при коммите). В этом уроке разберём современный «джентльменский набор»: ruff, black, mypy и pre-commit.

## Линейтер ruff

`ruff` — это очень быстрый линтер на Rust, который объединяет функциональность нескольких старых инструментов (flake8, pyflakes, isort). Он умеет:

- находить неиспользуемые импорты и переменные;
- находить неопределённые имена (опечатки);
- находить «подозрительные» конструкции (например, `== True` вместо `is True`);
- сортировать импорты;
- автоматически исправлять многие проблемы.

Установка и запуск:

```bash
python -m pip install ruff
python -m ruff check calc.py
```

По умолчанию включается базовый набор правил, но можно включить все: `python -m ruff check --select ALL calc.py`. Многие ошибки ruff исправляет сам:

```bash
python -m ruff check --fix calc.py
```

Пример «плохого» файла, который ruff сразу заметит:

```python
import os  # F401: неиспользуемый импорт

def add(a, b):
    return a + b

if add(1, 2) == True:  # E712: сравнение с True через ==
    print("ok")
```

## Форматтер black

`black` — «бескомпромиссный» форматтер: он берёт твой код и приводит его к единому стилю, почти не оставляя вариантов. Смысл в том, чтобы убрать споры «где ставить пробелы» — black решает это за всех. Запуск:

```bash
python -m pip install black
python -m black calc.py
```

Black переставит кавычки, отступы, переносы длинных строк. Код станет однообразным во всём проекте, а в diff-ах Git исчезнут «шумные» правки пробелов.

## Проверка типов mypy

Аннотации типов (`def f(x: int) -> str`) Python игнорирует при выполнении — это просто документация для людей и инструментов. `mypy` читает их и проверяет, не противоречат ли фактические значения аннотациям:

```bash
python -m pip install mypy
python -m mypy calc.py
```

Пример ошибки, которую поймает mypy:

```python
def price_with_tax(price: float, tax: float = 0.13) -> str:
    return price * (1 + tax)  # mypy: ожидается str, а на самом деле float
```

`mypy` найдёт место, где функция обещает вернуть `str`, а возвращает `float`. Так многие классы ошибок вылавливаются за секунду, ещё до запуска программы. Если в каком-то месте проверку нужно намеренно отключить, используют комментарий `# type: ignore` — но это скорее исключение, чем правило.

## pre-commit: всё это — автоматически

Хуки `pre-commit` запускают линтеры и прочие проверки **автоматически при каждом `git commit`**. Если проверка падает — коммит блокируется. Так «грязный» код просто не попадает в репозиторий. Настройка — файл `.pre-commit-config.yaml` в корне проекта:

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.11.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.15.0
    hooks:
      - id: mypy
```

После создания файла один раз выполни:

```bash
python -m pip install pre-commit
pre-commit install
```

Теперь при каждом коммите ruff и mypy прогонятся автоматически. Указанные версии (`rev`) стоит проверить на момент установки — бери актуальные.

## Итог урока

Все четыре инструмента решают одну проблему: они заменяют ручные проверки и перечитывание на автоматические. ruff находит ошибки, black убирает споры об оформлении, mypy ловит несоответствия типов, а pre-commit связывает всё это с git. Теперь попробуй настроить такой конвейер у себя.

### Разбор 1
Одно из возможных решений. После правок `calc.py` выглядит так:

```python
def add(a: int, b: int) -> int:
    return a + b


def multiply(x: int, y: int) -> int:
    result = x * y
    return result


if add(1, 2):
    print("three")
```

Что было исправлено и почему:

1. **`import os`** — удалён: он нигде не используется (ruff: F401).
2. **`== True`** — заменено на `if add(1, 2):`: сравнение с `True` через `==` избыточно (ruff: E712), булево значение можно использовать напрямую.
3. **Аннотации** — добавили `a: int`, `b: int`, `-> int` и так далее: теперь mypy может проверить согласованность типов. Без аннотаций mypy в режиме по умолчанию часто просто не находит что проверять в простых функциях.
4. **Код правила** — каждый флаг ruff имеет код: `F` — ошибки, связанные со «здоровьем» кода (пропущенные импорты, неопределённые имена), `E` — стилевые ошибки (пробелы, кавычки, сравнения). Код помогает понять и категорию проблемы, и что именно чинить.

Проверка:

```bash
python -m ruff check calc.py       # чисто
python -m mypy calc.py             # чисто
```

Если mypy ругается на отсутствие аннотаций в отдельных местах — добавь их или опиши типы полностью. Что касается pre-commit: после `pre-commit install` хуки будут запускаться при каждом коммите; в первый раз они могут «загружать» окружение — это нормально.

Главный вывод: инструменты не мешают, а экономят время. Они ловят то, что глаз устаёт замечать после часа правок, и делают код предсказуемым для коллег по команде.

### Разбор 2
Решение:

```python
def load_config(path):
    with open(path) as data:
        return data.read()


def parse(raw):
    try:
        return int(raw)
    except ValueError:
        return None


print(load_config("config.txt"))
print(parse("abc"))
```

Что исправил `ruff --fix` автоматически: удалил `import sys` (F401) и переменную `unused_var` (F841). Чего он не тронул: голый `except:` (E722) и `open()` без закрытия (SIM115). Голый `except` опасен тем, что ловит вообще все исключения, включая `KeyboardInterrupt` и `SystemExit`, и прячет настоящие ошибки; поэтому мы сузили его до `except ValueError`. `open()` в `with`-блоке гарантированно закрывает файл даже при исключении — это стандарт работы с ресурсами. Похожий принцип действует для баз данных, сетевых соединений и файлов: любой открытый ресурс должен быть закрыт.

### Разбор 3
Решение:

```python
def total(prices: list[float]) -> float:
    return round(sum(prices), 2)


def discount_price(price: float, percent: float) -> float:
    if percent > 0:
        return price * (1 - percent / 100)
    return price


print(total([10.5, 5.25]))
print(discount_price(100.0, 10.0))
```

Первая ошибка mypy: `total` объявлена как `-> str`, а возвращает `round(...)` — число. Мы поменяли аннотацию на `-> float`: тип стал соответствовать реальности. Вторая ошибка: `discount_price` в одной ветке возвращает число, а в другой — `None`, что противоречит `-> float`. Здесь два честных варианта: либо вернуть `price` без скидки при `percent <= 0` (так и сделано), либо объявить `-> Optional[float]`. Важно понимать: mypy не исполняет код, он статически проверяет, что обещанное совпадает с фактическим, — и лучший способ «починить» ошибку не в том, чтобы подавить её комментарием, а в том, чтобы сделать типы честными.

Что делает `ruff`?

- Запускает программу с отладчиком
- Ищет ошибки и проблемы стиля в коде, умеет их автоматически исправлять
- Компилирует Python-код в машинный
* Правильный ответ: Ищет ошибки и проблемы стиля в коде, умеет их автоматически исправлять
Это линтер: он находит неиспользуемые импорты, неопределённые имена, стилевые нарушения и многое другое.

Что делает `black`?

- Запускает тесты
- Приводит оформление кода к единому стилю автоматически
- Оптимизирует скорость выполнения программы
* Правильный ответ: Приводит оформление кода к единому стилю автоматически
Black — форматтер: он переписывает код в едином стиле, чтобы команда не спорила об оформлении.

Какую задачу решает `mypy`?

- Проверяет соответствие значений аннотациям типов
- Измеряет время выполнения функций
- Деплоит код на сервер
* Правильный ответ: Проверяет соответствие значений аннотациям типов
Mypy — статическая проверка типов: он ловит, например, функцию, которая обещает вернуть `str`, а возвращает `float`.

Когда запускаются хуки `pre-commit`?

- При каждом запуске программы
- При каждом `git commit`
- При каждом сохранении файла
* Правильный ответ: При каждом `git commit`
Хуки выполняются перед коммитом, и если проверка провалилась — коммит блокируется.

Что означает комментарий `# type: ignore`?

- Отключить проверку типов для этой строки
- Удалить строку из кода
- Добавить строку в тесты
* Правильный ответ: Отключить проверку типов для этой строки
Это намеренное отключение mypy в конкретном месте — использовать его стоит редко и с объяснением.
Что делает комментарий `# noqa` в строке кода?

- Отключает предупреждения линтера для этой строки
- Добавляет строку в автогенерацию документации
- Помечает строку как обязательную для тестов
* Правильный ответ: Отключает предупреждения линтера для этой строки
`noqa` (no quality assurance) просит линтер игнорировать именно эту строку — используется точечно и с объяснением.

Что произойдёт, если mypy найдёт несоответствие типов?

- Mypy сообщит об ошибке, но код останется исполняемым
- Python откажется запускать программу
- Код будет автоматически исправлен
* Правильный ответ: Mypy сообщит об ошибке, но код останется исполняемым
Mypy работает статически и не влияет на выполнение: он лишь подсвечивает потенциальные проблемы до запуска.

Зачем в pytest используют фикстуры (fixtures)?

- Чтобы подготовить окружение (данные, объекты) перед тестами и очистить его после
- Чтобы ускорить выполнение тестов
- Чтобы скрыть код тестов от других разработчиков
* Правильный ответ: Чтобы подготовить окружение (данные, объекты) перед тестами и очистить его после
Фикстуры устраняют дублирование: общая подготовка живёт в одном месте и переиспользуется в нескольких тестах.
