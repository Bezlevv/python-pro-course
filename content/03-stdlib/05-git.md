Git — это система контроля версий: инструмент, который хранит всю историю изменений кода. С его помощью можно откатиться к любой старой версии, работать над несколькими фичами одновременно и сотрудничать с другими программистами. Для питониста Git обязателен: без него не обходится ни один проект на GitHub, GitLab или Bitbucket.

## Установка и настройка

Скачай Git с официального сайта [git-scm.com](https://git-scm.com/) и установи. После установки один раз представимся — эти данные попадут в каждый коммит:

```bash
git config --global user.name "Аня"
git config --global user.email "anya@example.com"
```

## Первый репозиторий

Репозиторий — это папка, за которой Git следит. Создаём его в папке проекта:

```bash
git init
```

Теперь посмотрим на состояние проекта:

```bash
git status
```

Git покажет все файлы, которые ещё не отслеживаются. Добавляем их в «индекс» (staging) и фиксируем:

```bash
git add .                 # добавить все файлы
git commit -m "Первая версия программы"
```

`git add` подготавливает изменения, `git commit` делает снимок: он запоминает все подготовленные изменения вместе с сообщением. История коммитов:

```bash
git log --oneline
```

## Три состояния файла

Файл в Git живёт в одном из трёх состояний: **изменён** (modified) — ты правил его, но ещё не добавил; **подготовлен** (staged) — добавлен через `git add`, но не зафиксирован; **зафиксирован** (committed) — сохранён в коммите. Цикл работы: правишь файл → `git add` → `git commit`.

## .gitignore

Не всё нужно хранить в истории: временные файлы, секреты, виртуальные окружения. Для этого создают файл `.gitignore`:

```
__pycache__/
*.pyc
.env
venv/
```

Теперь Git будет игнорировать перечисленные файлы.

## Ветки

Ветка — это отдельная линия разработки. Например, основная ветка называется `main`, а новую фичу делают в ветке `feature`, не трогая основной код:

```bash
git switch -c feature     # создать и переключиться на ветку feature
# ... правим код ...
git add .
git commit -m "Добавлена новая функция"
git switch main            # вернуться в основную ветку
git merge feature          # слить изменения из feature в main
```

Ветки позволяют экспериментировать безопасно: даже если фича не получилась, основная ветка остаётся рабочей.

## GitHub: публикация

GitHub — облачный сервис для хранения Git-репозиториев. Создай пустой репозиторий на сайте GitHub и привяжи его к локальному:

```bash
git remote add origin https://github.com/anya/my-project.git
git push -u origin main
```

Теперь проект в облаке. Забрать изменения других участников — `git pull`, скопировать чужой проект — `git clone https://github.com/anya/my-project.git`. А чтобы предложить свои изменения в чужой проект, используют форк и pull request.

### Задача 1
Создай мини-проект `hello_git.py` и проведи его через Git:

1. Инициализируй репозиторий в папке проекта (`git init`);
2. Напиши первую версию программы (например, вывод приветствия) и сделай коммит с сообщением `Первая версия`;

5. Вернись в основную ветку и смержи `feature` в неё;
6. Выведи `git log --oneline --graph --all` и убедись, что в графе видны ответвление и слияние.

Если есть аккаунт на GitHub — создай пустой репозиторий, привяжи `origin` и запушь ветку `main`. Если нет — просто запиши команды, которые для этого понадобятся.

Ожидаемый результат: в графе коммитов три коммита в основной ветке и один коммит, добавленный из `feature`.

4. Выполни `git add .` и `git commit -m "Добавлен .gitignore"`.

Ожидаемый результат: `git status` после коммита чистый, а сами мусорные файлы остались на диске, но не попали в историю.

### Задача 3
Потренируйся видеть изменения до и после индексации:

1. Открой `hello_git.py` и добавь в него новую строку (например, комментарий или print);
2. Выполни `git diff` — убедись, что изменение видно как «изменённое»;
3. Выполни `git add .` и затем `git status` — файл должен перейти в состояние «подготовлен» (staged);
4. Выполни `git commit -m "Правка hello_git.py"`.

Ожидаемый результат: сначала `git diff` показывает разницу, после `git add` — нет (изменения «заморожены» в индексе), а `git status` показывает файл в зоне staging.

### Задача 4
Скопируй проект через `git clone`:

1. Из родительской папки выполни `git clone <путь к папке проекта> clone_copy`;

3. Выполни `git log --oneline` — убедись, что история коммитов совпадает с оригиналом;
4. Запусти `hello_git.py` из копии.

Ожидаемый результат: папка `clone_copy` содержит полную копию проекта вместе с историей, а запуск программы работает.

4. Проверь, что в журнале появилась именно эта правка.

Ожидаемый результат: последняя строка `git log` показывает автора `Код Мастер <master@example.com>` и правильное сообщение.

### Подсказка 1
Используй `git switch -c feature`, чтобы создать ветку и сразу переключиться на неё. Перед слиянием вернись в `main`: `git switch main`, затем `git merge feature`. Смотри граф через `git log --oneline --graph --all`. Если `git status` показывает лишние файлы — создай `.gitignore`.

### Подсказка 2
Файл `.gitignore` — обычный текстовый: каждая строка — шаблон. Учти: `venv/` игнорирует папку с содержимым, `*.pyc` — любые файлы с таким расширением. Проверяй эффект через `git status` до коммита: игнорируемые файлы вообще не должны появляться в выводе.

### Подсказка 3
`git diff` показывает изменения ещё не добавленных в индекс файлов. После `git add` тот же дифф становится пустым — изменения «переехали» в индекс. Чтобы увидеть подготовленные изменения, существует `git diff --cached`, но в задаче достаточно убедиться, что после `git add` вывода `git diff` нет.

### Подсказка 4
`git clone <путь>` копирует репозиторий вместе с историей. Указывай путь к папке проекта, а не к файлу; копия создастся как подпапка с именем `clone_copy`. Внутри копии `git log --oneline` должен показать те же коммиты, что и в оригинале.

### Подсказка 5
Без `--global` настройки применяются только к текущему репозиторию и хранятся в `.git/config`. Формат `%an` — имя автора, `%ae` — его почта, `%s` — сообщение коммита. Проверить настройки можно через `git config user.name`.

### Разбор 1
Последовательность команд:

```bash
# 1. Репозиторий
cd my_project
git init

# 2. Первая версия
# hello_git.py: print("Привет!")
git add .
git commit -m "Первая версия"

# 3. Вторая версия
# добавили функцию bye() с print("Пока!")
git add .
git commit -m "Добавлено прощание"

# 4. Ветка feature
git switch -c feature
# добавили функцию today() с выводом текущей даты
git add .
git commit -m "Добавлена функция даты"

# 5. Слияние
git switch main
git merge feature

# 6. Граф
git log --oneline --graph --all
```

Граф после слияния будет выглядеть примерно так:

```
*  3f2a1e (HEAD -> main) Merge branch 'feature'
|\
| * 8c44b2 (feature) Добавлена функция даты
* | 5d991c2 Добавлено прощание
|/
* a1b2c3 Первая версия
```

Публикация на GitHub:

```bash
git remote add origin https://github.com/<твой-логин>/hello_git.git
git push -u origin main
```

Разбор шагов. `git init` создаёт скрытую папку `.git` — здесь Git хранит всю историю. `git add .` готовит все изменения, `git commit -m` фиксирует их: каждый коммит — это снапшот проекта с сообщением. Ветка `feature` создаётся командой `git switch -c feature`: рабочий код в ней не мешает `main`. Когда фича готова, мы переключаемся на `main` и выполняем `git merge feature` — Git находит общего предка и объединяет линии, поэтому в графе видна «вилка» (ответвление) и «стрелка» (слияние). `git log --oneline --graph --all` показывает граф всех веток. Наконец, `git push -u origin main` отправляет локальную ветку `main` на GitHub и запоминает её как удалённую по умолчанию — дальше достаточно простого `git push`.

### Разбор 2
Команды и файлы:

```bash
mkdir venv __pycache__
touch cache.pyc .env
# создаём .gitignore с содержимым:
# venv/
# __pycache__/
# *.pyc
# .env

git status
git add .
git commit -m "Добавлен .gitignore"
```

Результат: `git status` до коммита показывает только `.gitignore` и исходные файлы — мусор не отображается; после коммита `git status` чистый.

Разбор шагов. `.gitignore` — текстовый файл, каждая строка которого — шаблон игнорирования. `venv/` и `__pycache__/` с завершающим слэшем отмечают папки целиком, `*.pyc` охватывает любые скомпилированные файлы, а `.env` скрывает файл с секретами. Эффект виден уже в `git status`: Git не показывает игнорируемые файлы среди неотслеживаемых — они словно не существуют для него, хотя остаются на диске. Это правило нужно усвоить сразу: никогда не коммить `venv`, `__pycache__`, секреты и большие временные файлы — они либо раздувают историю, либо утекают в общий доступ. Игнорирование по шаблонам работает и для вложенных папок, поэтому одного файла `.gitignore` в корне обычно достаточно.

### Разбор 3
Команды:

```bash
# правим hello_git.py, добавляем новую строку
git diff                # покажет изменение
git add .
git status              # файл в состоянии staged
git diff                # теперь пусто
git commit -m "Правка hello_git.py"
```

Разбор шагов. `git diff` показывает разницу между рабочей папкой и индексом (staging): видны добавленные и удалённые строки. После `git add .` изменения перемещаются в индекс, и тот же `git diff` становится пустым — расхождений между рабочей папкой и индексом больше нет. При этом `git status` подсказывает состояние: строка `Changes to be committed` (изменения, готовые к коммиту) означает, что файл подготовлен. Именно этот трёхшаговый цикл — правка → `git add` → `git commit` — составляет основу повседневной работы с Git. Полезно привыкнуть смотреть `git diff` перед коммитом: так ты видишь ровно то, что собираешься зафиксировать, и не закоммитишь случайную правку.

### Разбор 4
Команды:

```bash
# из родительской папки
git clone my_project clone_copy
cd clone_copy
git log --oneline
python hello_git.py
```

Разбор шагов. `git clone <путь>` создаёт полную копию репозитория — вместе со всем содержимым рабочей папки и всей историей коммитов. Это не «копирование файлов»: копия содержит скрытую папку `.git` с полным журналом, поэтому `git log --oneline` внутри `clone_copy` показывает те же коммиты, что и в оригинале. Так работает и `git clone https://github.com/...` для публичных проектов: ты получаешь рабочую копию чужого кода и можешь свободно её изучать, запускать и менять локально, не влияя на оригинал. Поскольку `clone_copy` — самостоятельный репозиторий, дальнейшие коммиты в нём не затронут оригинальный проект. Это главный способ начать работу с чужим кодом.

### Разбор 5
Команды:

```bash
git config user.name "Код Мастер"
git config user.email "master@example.com"

# правим hello_git.py
git add .
git commit -m "Правка от Код Мастера"

git log -1 --format='%an <%ae> %s'
```

Результат:

```
Код Мастер <master@example.com> Правка от Код Мастера
```

Разбор шагов. Без флага `--global` команды `git config` меняют настройки только текущего репозитория — они хранятся в файле `.git/config` и перекрывают глобальные значения. Это удобно, когда в разных проектах ты выступаешь под разными именами (например, рабочая и личная почта). Формат `git log -1 --format='%an <%ae> %s'` выводит для последнего коммита имя автора (`%an`), его почту (`%ae`) и сообщение (`%s`). Теперь видно, что именно этот коммит подписан локальными данными, а не глобальными. Настройка личности важна не только для красоты: по имени и почте автора в командных проектах определяют, кому писать про код-ревью и кто за что отвечает.
